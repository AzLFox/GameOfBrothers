# Роадмап новой фичи GoB

Навык оформляет план внедрения новой возможности проекта **GameOfBrothers** как
документ `docs/<slug>-roadmap.md` — в едином формате с уже существующими роадмапами.
Цель формата: разбить фичу на **фазы, каждая из которых — одна рабочая сессия и один
небольшой коммит**, с готовым промптом-инструкцией и проверяемыми критериями приёмки.

Читай перед работой: [docs/INDEX.md](../../../docs/INDEX.md) и [CLAUDE.md](../../../CLAUDE.md).
Образцы формата (ссылайся на них, а не пересказывай): `docs/auth-roadmap.md`,
`docs/create-hero-roadmap.md`, `docs/visual-roadmap.md`, `docs/mobile-visual-roadmap.md`.

## Как работать

1. **Пойми фичу.** Если запрос расплывчатый — уточни у пользователя цель, границы
   (что входит/не входит), затронутые слои (сервер / хранилище / фронтенд), и есть ли
   особые доменные правила (формулы листа, лимиты группы, префиксы id — см. CLAUDE.md).
   Не выдумывай требования: то, чего нет ни в запросе, ни в коде, — спроси.
2. **Изучи, что уже есть в коде.** Роадмап опирается на реальные файлы (`server/server.js`,
   `server/store.js`, `public/js/*`). Прежде чем писать фазы, найди точки интеграции —
   промпты фаз должны называть конкретные файлы, функции и маршруты, а не абстракции.
3. **Выбери ветку и префикс фаз.** Одна ветка на фичу (`feature-name`, от `develop`,
   merge обратно в `develop`). Короткий буквенный префикс фаз, привязанный к фиче:
   `A1…` (auth), `C1…` (create-hero), `M1…` (mobile). Для чисто визуальных фич
   допустимы сквозные номера `1, 2, 3…` c под-фазами (`6b`).
4. **Декомпозируй на фазы** по принципу «одна фаза = одна сессия = один коммит».
   Ранние фазы дают работающий минимум (MVP), поздние — полировку/опции. Явно помечай
   необязательные фазы `(опционально)` и выноси их в скобки в блоке «Порядок».
5. **Заполни шаблон** `assets/roadmap-template.md` (скопируй в `docs/<slug>-roadmap.md`
   и адаптируй). Структура разделов — ниже.
6. **Зарегистрируй документ** в [docs/INDEX.md](../../../docs/INDEX.md): строка в
   разделе «Проектная документация» — `[<slug>-roadmap.md](<slug>-roadmap.md) — <описание>.`
   Если фича крупная и достойна отдельного трекинга — добавь заметку в `docs/TO-DO.md`.
7. **Не начинай реализацию**, если пользователь просил именно план. Роадмап — это
   план, а не код. После согласования плана можно приступать к фазе A1/C1/….

## Структура документа

Соблюдай порядок и заголовки — по ним формат узнаётся.

### 1. Заголовок и шапка
```
# <Фича> — <короткая формулировка цели>

**Ветка:** `feature-name` (от `develop`, merge в `develop`)
**Цель:** <одна фраза, что получаем в итоге>
```
При необходимости добавь строки шапки, релевантные фиче: `**Хранилище (v1):**`,
`**Стек:**`, `**Приоритеты:**`. Одна фраза-напоминание: «Каждая фаза — отдельная
сессия работы. Выполнять по порядку.»

### 2. Принципы
Маркированный список инвариантов и ограничений фичи — то, что нельзя нарушать ни в
одной фазе. Отсюда потом растут «Быстрые правила». Примеры инвариантов GoB: не трогать
игровые формулы (`maxHp = str×4 + hpBonus` и т.д.), не переписывать на React/Vue, не
ломать desktop при мобильных правках, `prefers-reduced-motion`, разделение
builtin/пользовательских данных.

### 3. (Опционально) Модель данных / параметры
Если фича вводит новые сущности, поля или ассеты — добавь до фаз: таблицу параметров
(как размеры портрета в create-hero), пример JSON-записи, таблицу ключей хранилища,
описание заглушек/дефолтов. Пропусти, если фича этого не требует.

### 4. Фазы
Ядро документа. Каждая фаза — блок, отделённый `---`:

```
## Фаза <ID> — <краткое название>

**Промпт:**
> 1. <конкретный шаг: файл, функция, маршрут>
> 2. …
> 3. …

**Критерии готовности:**
- [ ] <проверяемый результат, а не «сделано хорошо»>
- [ ] …
```

- **Промпт** — цитата (`>`) с **нумерованным списком конкретных шагов**. Это
  готовая инструкция для отдельной сессии: называй реальные файлы, функции, эндпоинты,
  id элементов. Можно начать с вводной фразы, затем шаги. Пиши так, чтобы исполнителю
  не пришлось догадываться, где интегрироваться.
- **Критерии готовности** (в auth-роадмапе — «Критерии») — чек-лист `- [ ]`
  **объективно проверяемых** результатов. По ним делается приёмка фазы. Отмечай
  выполненное `- [x]` по мере готовности.
- **Статус в заголовке** по мере работы: `(✅ готово)`, `✅`, `(частично)`.
- **(Опционально) `**Реализовано:**`** — короткая прозой запись, что именно и в
  каких файлах сделано (удобно для истории; см. mobile-роадмап).

### 5. Порядок
Последовательность выполнения, необязательные фазы — в скобках. Часто в код-блоке:
```
C1 → C2 → C3 → C4 → C5 → (C6) → (C7)
```
Одной фразой: какие фазы дают MVP, а какие можно отложить.

### 6. Быстрые правила для всех фаз
Сжатая выжимка, применимая к каждой фазе:
- Ветка → куда merge.
- Формат коммитов: `feat(<scope>): <фаза/суть>` / `fix(<scope>): …` (scope = фича).
- Инварианты домена (не React/Vue; логика листа важнее эффектов; не трогать формулы).
- Каждая фаза — маленький коммит; после фазы — smoke-проверка в браузере/через `node server/server.js`.

### 7. (Опционально) Бюджеты и smoke-сценарии
Для фич с измеримыми целями — таблица «Бюджеты» (метрики и цели, как в mobile-роадмапе).
Для потоков с приёмкой — «Smoke-сценарии»: пронумерованные end-to-end проверки, включая
регрессию существующего поведения.

## Стиль

- Документ и коммиты — **на русском** (правило проекта, см. CLAUDE.md).
- Шаги в промптах — императив и конкретика; критерии — проверяемые факты, не оценки.
- Учитывай реальную архитектуру GoB (монолитный `server/server.js`, файловый JSON в
  `server/store.js`, ванильные `GobXxx`-модули, SSE-синхронизация листа, `rev`-блокировка).
  Не предлагай сборщик, БД или фреймворк, если пользователь явно этого не просит.
- Пустой slug выбирай коротким и латиницей: `docs/<slug>-roadmap.md` (напр. `parties`,
  `dice`, `chat`).

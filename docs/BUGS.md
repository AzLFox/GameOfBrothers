## B1. Нет взаимного исключения: два мастера могут вести одну группу одновременно

Замысел: любой ГМ может взять любую свободную группу, но **не одновременно** с другим —
блокировкой служит `gmUserId` + проверка `canGmAccessGroup`.

Фактически блокировка не сохраняется: `normalizePartyGroup()` не переносит `gmUserId`/`gmAssignedAt`
в возвращаемый объект, а `savePartyGroup()` пишет объект целиком (`writeJson`, без мерджа), поэтому
`PUT /api/gm/session`, делающий `normalizePartyGroup({ ...group, gmUserId })`, сохраняет группу
**без** `gmUserId`. Подтверждено на рантайм-данных: в `server/data/parties/grp_*.json` ключа
`gmUserId` нет вообще.

Следствия:
- `canGmAccessGroup()` всегда возвращает `true` (условие `!group.gmUserId`), ошибка
  «Группа ведётся другим мастером» недостижима — ограничение «не одновременно» не работает.
- В сводке групп (`gmGroupSummary`) `gmUserId` пуст, `isActiveGm` всегда `false`.

Файлы: [../server/server.js:301](../server/server.js#L301) (`normalizePartyGroup`),
[../server/server.js:445](../server/server.js#L445) (`canGmAccessGroup`),
[../server/server.js:811](../server/server.js#L811) (`PUT /api/gm/session`),
[../server/store.js:132](../server/store.js#L132) (`savePartyGroup`).

Фикс: сохранять `gmUserId`/`gmAssignedAt` в `normalizePartyGroup` (или писать их в обход
нормализации) — **обязательно вместе с механизмом освобождения группы** (см. [TO-DO.md](TO-DO.md),
«освобождение группы / lease»), иначе группа навсегда залипнет за первым открывшим её мастером.

## B2. Аккаунт ГМ отображается как аккаунт игрока при создании группы

При создании группы аккаунт мастера показывается как обычный игрок — роль GameMaster в этом
интерфейсе не учитывается. Вероятная причина: регистрация всегда пишет `role: 'player'`
([../server/server.js:199](../server/server.js#L199)), а UI создания/отображения группы
([../public/js/gob-group.js](../public/js/gob-group.js) — `createGroup`,
[../public/js/group.js](../public/js/group.js)) не различает роль, поэтому ГМ попадает в список как игрок.

Нужно уточнить точку отображения и показывать роль ГМ корректно. Связано с идеей «явный элемент ГМ
в модели группы» и «нет способа выдать/учесть роль GameMaster» — см. [TO-DO.md](TO-DO.md).

## B3. `PUT /api/me/sheets/:charId` не валидирует тело

Сервер принимает произвольный JSON и пишет его как есть — серверной нормализации листа нет
(`defaultSheetForCard` используется только при создании). Теперь, когда в чужой лист может писать и
мастер (см. [TO-DO.md](TO-DO.md), «мастер правит листы героев» — сделано), отсутствие валидации
превращается из мелочи в риск целостности данных и безопасности.

Фикс: добавить `normalizeSheet()` по аналогии с `normalizePartyGroup` и прогонять тело через него
перед записью.

## B4. Щиты дают пассивную защиту вместо активной проверки

Замысел: щит **не** должен давать пассивную защиту. Его значение применяется только при удачной
проверке в момент получения урона; два щита (в обеих руках) = две отдельные проверки.

Фактически класс `shield` ([../public/js/item-catalog.js:89](../public/js/item-catalog.js#L89)) даёт
модификатор `armor` (`type: 'flat'`), который постоянно вливается в боевую строку «Защита» через
`sumEquipmentMods` ([../public/js/character.js:709](../public/js/character.js#L709)) — то есть щит
работает как пассивная броня.

Фикс: исключить `armor` щита из пассивного агрегата и переносить его значение в активный расчёт
входящего урона (см. [TO-DO.md](TO-DO.md), кнопка «получить пизды» — С2·3, шаг «Щит в руке»).

## B5. Двуручное оружие затирает предмет в другой руке

При установке двуручного оружия в редактируемую руку `reconcileHands`
([../public/js/character.js:3627](../public/js/character.js#L3627)) пишет зеркало во вторую руку
(`sheet.equipment[other] = mirror`, [:3635](../public/js/character.js#L3635)) — предмет, который там
был, молча удаляется.

Нужно **запрещать** экипировку двуручного оружия, если другая (не редактируемая в данный момент)
рука занята: не давать выбрать двуручный класс / показывать предупреждение, пока рука не
освобождена, вместо тихого удаления.

## B6. На телефоне перенос из снаряжения в рюкзак требует одновременного зажатия и тапа

Чтобы переложить вещь снаряжение → рюкзак на телефоне, сейчас нужно **одновременно** держать вещь и
тапнуть по слоту рюкзака. Нужен последовательный флоу: зажатие/тап **выделяет** вещь, следующий тап
по слоту — **переносит** (без одновременного удержания и нажатия).

## 🎯 Целевая модель «Стол мастера» ↔ группы

Желаемое поведение связки ГМ и групп (объединяет несколько задач ниже и баги
[B1](BUGS.md#b1-нет-взаимного-исключения-два-мастера-могут-вести-одну-группу-одновременно),
[B2](BUGS.md#b2-аккаунт-гм-отображается-как-аккаунт-игрока-при-создании-группы)):

- **ГМ имеет доступ ко всей функциональности групп** — не только правка листов героев (сделано,
  см. ниже), а весь функционал группы: состав, отряд, приглашения и т. д.
- **В модель группы добавить явный элемент «ГМ»** (слот мастера), а не только технический
  `gmUserId`-замок. Группа должна знать своего ведущего как часть данных.
- **Группа с назначенным ГМ не отображается другим ГМам** — взаимное исключение. Упирается в баг
  [B1](BUGS.md#b1-нет-взаимного-исключения-два-мастера-могут-вести-одну-группу-одновременно):
  сейчас `gmUserId` не сохраняется, поэтому «занята/свободна» не различается.
- **Когда ГМ выходит из группы, она снова свободна** — освобождение блокировки при выходе со стола /
  смене группы / логауте, плюс TTL (lease) на случай оборванной сессии. Чинить **строго вместе** с
  багом [B1](BUGS.md#b1-нет-взаимного-исключения-два-мастера-могут-вести-одну-группу-одновременно),
  иначе группа залипнет за первым мастером навсегда.
- **У ГМа — список всех свободных групп.** Основа есть (`gmGroupSummary`), но из-за бага
  [B1](BUGS.md#b1-нет-взаимного-исключения-два-мастера-могут-вести-одну-группу-одновременно)
  `gmUserId` пуст и `isActiveGm` всегда `false`.
- **Игрок может пригласить ГМа в группу.** Отдельного флоу приглашения ГМ сейчас нет.
- **ГМу нужна функциональность сообщений/ящика** — для приёма приглашений. Сейчас
  `gob-invites.js` / `messages.json` работают на стороне игроков; механизм нужно распространить на ГМа.

## 🧩 Функциональные предложения

### Способ выдать роль GameMaster из приложения
Роль берётся только из env `GOB_GM_USERNAMES` ([../server/auth.js:133](../server/auth.js#L133)) либо
ручной правкой поля `role` в JSON пользователя; регистрация всегда ставит `role: 'player'`
([../server/server.js:122](../server/server.js#L122)). Нет админ-панели/флоу назначения.
Как минимум — задокументировать переменную `GOB_GM_USERNAMES` в README/деплое.

### Управление составом группы со «стола»
С экрана GM нельзя добавить/убрать участника или переименовать отряд — пикер прямо пишет, что
группы создают игроки на листе персонажа ([../public/gm.html](../public/gm.html)). Очевидный пробел
для роли ведущего.

### Полноценные слоты для кольца/ожерелья/питомца
`EXTRA_SLOTS` (ring/necklace/pet, [../public/js/character.js:291](../public/js/character.js#L291)) не

### Перестановка предметов внутри рюкзака
drag-drop работает рюкзак↔снаряжение (`canMove` [../public/js/character.js:2403](../public/js/character.js#L2403)),
но переложить предмет из одного слота рюкзака в другой нельзя. Добавить перемещение слот-в-слот
внутри рюкзака — так же, как между слотами снаряжения.

### Закрытие редактора снаряжения без сохранения
Редактор слота применяет правки сразу (`apply` → `scheduleSave`, [../public/js/character.js:3740](../public/js/character.js#L3740)).
Нужна возможность выйти **без изменений**: при закрытии — диалог «Сохранить изменения? Сохранить /
Нет». То есть перейти с live-apply на черновик с подтверждением.

## 🧙 Инструменты ГМа

### Шаблоны НПС
У ГМа нет заготовок персонажей-НПС. Нужны шаблоны НПС (быстрое создание противников/союзников с
листом), которыми ГМ наполняет стол.

**Источник данных — внешняя вики домена, а не код** (правила ролёвки ведутся отдельно от
GameOfBrothers): `C:\Users\shef\Claude\Projects\my_personal_assistant\wiki\GoB\`. Релевантные файлы:
- `Расы (GoB).md` — таблица-конструктор статблоков **9 рас × 4 роли** (Танк/Атакер/Колдун/Хиллер) +
  легенда чтения ячейки + множитель тира;
- `Сборка NPC (GoB).md` — метод: раса+роль → базовый статблок → ×тир → ×группировка (с примерами);
- `Группировки и особенности (GoB).md` — модификаторы группировок (Разбойник ×0.5 … Святой ×2.0,
  спецэффекты Нежити/Вампира/Механизма);
- `2026-07-07 Статблоки рас GoB (Gob_race.csv).md` — исходная дизайн-таблица ГМ (`raw/assets/Gob_race.csv`,
  Windows-1251);
- `characters/` — конкретные статблоки НПС (Михалыч, Некрос, Вуду и др.).

**Модель НПС ≠ лист игрока** — не выводить механику из кода PC:
- **HP задаётся напрямую** (ведущее число статблока), а не через `str×4`;
- защитные слои в скобках (`ув`/`защ`/`щит`) **плоско вычитаются из урона**; «щит» в статблоках = баблы;
- масштабирование: **тир ×1–4**, поверх — **множитель группировки**; множители перемножаются и
  применяются ко всему (кроме собственного спецэффекта группировки — он масштабируется только тиром);
- таблица **неполная** (ГМ прислал не всё), часть ячеек не расшифрована (`1D4в`, `1D12 ба`, `2×1`,
  `DMG = HP`) — считать неопределёнными.

То есть шаблон НПС — отдельная сущность (раса + роль + тир + группировка → производный статблок), а не
обычный `sheet` персонажа. Детали домена сверять с вики (путь выше), а не с кодом.

### Стол файта
Отдельный «боевой стол»: персонажи игроков текущей группы + НПС (противники и союзники). На нём можно:
- выбирать, **кто кого атакует** — это даёт нормальную реализацию кнопки «получить пизды»
  (см. С2·3 выше);
- кому передаются предметы;
- на кого кастуются спелы;
- показывать поверженных противников;
- разделять бойцов на **ближнюю и дальнюю** дистанции.

Крупная фича — оформлена роадмапом: [fight-table-roadmap.md](fight-table-roadmap.md)
(v1 — персонажи игроков, общий живой бой; фазы F1–F6, ветка `feature/fight-table`).

## 💾 Хранение и данные

### Каталог предметов GM живёт в `sessionStorage`
Пользовательские предметы, папки и их размещение хранятся в `sessionStorage`
([../public/js/gm-catalog-store.js:5](../public/js/gm-catalog-store.js#L5),
[:67](../public/js/gm-catalog-store.js#L67)), поэтому теряются при закрытии вкладки/сессии и не
синхронизируются между устройствами и с сервером. Ожидаемо — хотя бы `localStorage`, а лучше
хранить каталог на сервере в аккаунте мастера.

### Ящик сообщений не чистится и не ограничен
`messages.json` растёт без ограничений: принятые/отклонённые/прочитанные сообщения хранятся вечно
(принятые/отклонённые подарки скрываются из выдачи через `isPendingMailMessage`, но текстовые и
прочитанные остаются, а файл не подрезается). Нужна политика хранения/архивации и/или лимит.

### Read-modify-write по JSON без блокировок
> ✅ Для **листов персонажа** закрыто: у листа появился `rev`, сервер инкрементит его при записи,
> устаревший PUT получает 409 со свежей версией. Ниже — про оставшиеся файлы.

Приём/отклонение/пометка сообщений и правки групп читают → меняют → пишут файл целиком; при
одновременных запросах возможна потеря обновлений. Известное ограничение файлового хранилища —
приемлемо на текущем масштабе, но стоит держать в уме (очередь записи или атомарная запись с локом).

## 🧹 UX и технический долг

### Нет следа правок мастера
Лист хранит только `updatedBy` последней записи (`owner`/`gm`) — истории нет. Игрок не видит,
что именно поменял мастер: HP просто становится другим. Стоит завести журнал правок или хотя бы
уведомление игроку («мастер изменил HP: 12 → 9»).

### Обновление ящика только поллингом раз в 4 c
`gob-invites.js` опрашивает сервер каждые 4 секунды и по `focus`
([../public/js/gob-invites.js:506](../public/js/gob-invites.js#L506)). Теперь, когда в проекте есть
SSE для листов, поллинг ящика логично перевести на тот же механизм.

## ✅ Сделано

- **Мастер действует как владелец героя.** Мастер открывает лист любого героя своей активной группы
  (`resolveCharAccess`) и правит его как владелец: показатели, баффы/дебаффы, предметы, деньги — весь
  существующий лист. Правки применяются мгновенно и уезжают в хранилище **владельца**; открытый лист
  игрока обновляется через SSE (`/api/me/sheets/:charId/events`). Отдельная панель ГМ намеренно не
  строилась. Остаётся: аудит правок (см. выше) и серверная валидация тела
  ([B3](BUGS.md#b3-put-apimesheetscharid-не-валидирует-тело)).
